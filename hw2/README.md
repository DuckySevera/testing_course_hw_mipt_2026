# User stories для GitHub

## Выбор продукта

Для задания я взял GitHub. Им я пользуюсь почти каждый день, и в прошлом задании уже разбирал, как бы его изучал тестировщик без документации. Обе истории ниже связаны с главным риском, который я тогда выделил: права доступа должны одинаково работать везде — на сайте, через API и через git.

Истории написаны по шаблону «Как… я хочу… чтобы…». Критерии приёмки — в формате Given/When/Then (Дано / Когда / Тогда). Я старался, чтобы каждый критерий можно было однозначно проверить и превратить в тест-кейс.

---

## User story 1. Защита основной ветки

**Как** мейнтейнер репозитория,
**я хочу** запретить слияние pull request в ветку `main` без одобрения другого участника,
**чтобы** в основную ветку не попадал код, который никто, кроме автора, не проверил.

### Критерии приёмки

1. **Включение правила**
   - *Дано:* у пользователя роль admin в репозитории.
   - *Когда:* он открывает настройки защиты ветки `main`, включает «Требовать одобрение перед слиянием» и указывает минимум 1 одобрение.
   - *Тогда:* правило сохраняется и отображается в списке правил ветки.

2. **Слияние без одобрения запрещено**
   - *Дано:* правило включено, открыт PR в `main`, одобрений нет.
   - *Когда:* пользователь с правами write пытается смержить PR.
   - *Тогда:* кнопка «Merge» неактивна, рядом виден текст о том, что требуется одобрение.

3. **Нельзя одобрить свой PR**
   - *Дано:* правило включено.
   - *Когда:* автор PR пытается его одобрить.
   - *Тогда:* одобрение не засчитывается в количество обязательных.

4. **Слияние после одобрения**
   - *Дано:* PR одобрил другой участник с правами write.
   - *Когда:* автор нажимает «Merge».
   - *Тогда:* PR сливается в `main`.

5. **Сброс одобрения после новых изменений**
   - *Дано:* включена опция «Сбрасывать одобрения при новых коммитах», PR одобрен.
   - *Когда:* автор пушит новый коммит в ветку PR.
   - *Тогда:* одобрение сбрасывается, и слияние снова недоступно до нового одобрения.

6. **Правило работает во всех клиентах**
   - *Дано:* правило включено, одобрений нет.
   - *Когда:* пользователь пытается смержить PR через REST API или `gh pr merge`, либо сделать `git push` напрямую в `main`.
   - *Тогда:* операция отклоняется с понятным сообщением об ошибке.

## User story 2. Удаление участника из организации

**Как** владелец организации,
**я хочу** удалить участника из организации,
**чтобы** человек, который ушёл из команды, сразу потерял доступ к приватным репозиториям.

### Критерии приёмки

1. **Удаление участника**
   - *Дано:* пользователь — владелец организации, в организации есть участник X.
   - *Когда:* владелец выбирает X в списке участников и подтверждает удаление.
   - *Тогда:* X пропадает из списка участников и из всех команд организации.

2. **Подтверждение перед удалением**
   - *Дано:* владелец нажал «Удалить».
   - *Когда:* появляется диалог подтверждения.
   - *Тогда:* в нём указано, какие доступы потеряет пользователь, а удаление происходит только после явного подтверждения.

3. **Пропадает доступ через сайт**
   - *Дано:* X удалён.
   - *Когда:* X открывает ссылку на приватный репозиторий организации.
   - *Тогда:* он получает страницу 404, и содержимое репозитория не показывается.

4. **Пропадает доступ через git и API**
   - *Дано:* X удалён, у него остались SSH-ключ и личный токен.
   - *Когда:* X делает `git clone` или запрос к API приватного репозитория организации.
   - *Тогда:* доступ запрещён, данные не возвращаются. Доступ к его собственным репозиториям при этом сохраняется.

5. **Скорость отзыва доступа**
   - *Дано:* X удалён.
   - *Когда:* проходит не больше 1 минуты *(точное значение нужно уточнить у команды)*.
   - *Тогда:* все способы доступа из пунктов 3 и 4 уже не работают.

6. **Вклад участника сохраняется**
   - *Дано:* X раньше делал коммиты, PR и комментарии в репозиториях организации.
   - *Когда:* его удалили.
   - *Тогда:* его коммиты, PR и комментарии остаются в истории.

7. **Журнал действий**
   - *Дано:* X удалён.
   - *Когда:* владелец открывает журнал аудита организации.
   - *Тогда:* там есть запись о том, кто и когда удалил X.

8. **Нельзя удалить последнего владельца**
   - *Дано:* в организации единственный владелец.
   - *Когда:* он пытается удалить сам себя.
   - *Тогда:* действие запрещено, показывается сообщение, что сначала нужно назначить другого владельца.

## Вывод

В обеих историях часть критериев проверяет не только интерфейс. Пункт 6 первой истории и пункт 4 второй требуют, чтобы правило работало через API и git. Если проверить только кнопки на сайте, можно пропустить ситуацию, когда в интерфейсе действие запрещено, а через API — нет.

В пункте 5 второй истории есть значение, которое я не знаю наверняка (за сколько должен пропасть доступ). Без такой цифры критерий нельзя проверить, поэтому его нужно согласовать с командой до начала разработки.
