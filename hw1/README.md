# Как бы я изучал GitHub без документации

## Почему GitHub

Я пользуюсь GitHub почти каждый день: держу там свои проекты, смотрю чужой код, иногда пишу workflow для CI. Поэтому мне было интересно посмотреть на него не как пользователю, а как тестировщику, который пришёл в команду и ничего не знает.

Мне кажется, GitHub хорошо подходит для такого задания. Снаружи это «просто хранилище кода», но внутри там много всего: организации, команды, разные роли, защита веток, Actions, вебхуки, API, мобильное приложение. И если где-то ошибка в правах доступа, то утекает не картинка, а чей-то приватный код или секреты от продакшена. То есть цена бага высокая.

## С чего бы я начал

Первые два дня я бы вообще не пытался ничего ломать. Сначала надо понять, что это за продукт и как им пользуются нормальные люди.

**День 1.** Прошёл бы весь путь как новый пользователь: зарегистрировался, включил двухфакторку, создал репозиторий, склонировал, запушил коммит, сделал ветку, открыл PR, сам себе его одобрил и смержил. Параллельно рисовал бы карту: какие есть сущности (репозиторий, issue, PR, организация, команда и т.д.) и как они связаны. Получится что-то вроде mind map, к которой потом можно возвращаться.

**День 2.** Искал бы документацию там, где её «нет». У GitHub есть публичный changelog, форум GitHub Community, отзывы в сторах для мобильного приложения. Ещё есть GitHub CLI с открытым исходным кодом, и по его issues можно понять, на что жалуются пользователи и какие места в API странно себя ведут. Это почти бесплатный список проблемных зон.

**День 3.** Посмотрел бы, как продукт устроен снаружи. Открыл DevTools и смотрел бы, какие запросы уходят при обычных действиях. Попробовал бы REST и GraphQL API, завёл тестовый сервер для вебхуков. Что важно понять на этом этапе:

- одно и то же действие можно сделать через сайт, мобилку, `gh`, API и обычный `git push`. Значит, проверки прав должны работать везде одинаково, и это первое, что я бы проверял;
- часть вещей происходит не сразу. Поиск, статусы CI, вебхуки, пересчёт того, можно ли смержить PR, всё это работает в фоне. Значит, будут промежуточные состояния, когда данные в разных местах не совпадают.

Дальше, с 4 по 6 день, уже само тестирование, а последний день на то, чтобы собрать всё в отчёт и вопросы к команде.

## Что бы я проверял

### Основные сценарии

Это то, что должно работать всегда, и если сломалось, то сломалось у всех:

1. регистрация и вход, включая 2FA;
2. создание репозитория, clone, commit, push;
3. ветка → PR → ревью → merge (все три способа: merge commit, squash, rebase);
4. issue: создать, назначить, повесить метку, закрыть через `Fixes #12` в коммите;
5. форкнуть чужой репозиторий и прислать PR из форка;
6. запустить простой workflow в Actions.

### Pull request

Тут больше всего состояний, поэтому я бы прям расписал их и прошёл каждый переход. Самые интересные случаи, на мой взгляд:

- после approve автор делает force-push. Сбросится ли одобрение, если в настройках так указано?
- в целевую ветку что-то пушат, пока PR на ревью. Правильно ли пересчитываются конфликты?
- исходную ветку или форк удалили, а PR ещё открыт;
- у открытого PR меняют base-ветку;
- кто-то пытается смержить, пока обязательные проверки ещё не прошли.

### Права доступа

Это, по-моему, самое важное. Я бы сделал таблицу: по строкам роли (read, triage, write, maintain, admin, внешний коллаборатор, владелец организации), по столбцам действия (пушить, мержить, менять настройки, видеть секреты и т.д.). И прошёл бы её не только через сайт, но и через API и `git`. Если в интерфейсе кнопки нет, это ещё не значит, что через API действие тоже запрещено.

Ещё отдельно хочется проверить, что бывает, когда доступ **забирают**. Человека удалили из организации: перестаёт ли сразу работать его токен, SSH-ключ, уже открытая вкладка? Или какое-то время всё ещё можно что-то сделать?

Похожая история с переводом репозитория из приватного в публичный и обратно, с передачей репозитория другому владельцу, с форками приватных репозиториев.

### Когда несколько людей делают что-то одновременно

- двое редактируют описание одного issue. Чья версия останется и предупредят ли второго?
- двое одновременно нажимают «Merge»;
- push в одну ветку с двух машин.

### Окружение

Разные браузеры, телефон, медленный интернет, обрыв сети в момент отправки комментария. Тёмная тема, крупный шрифт, работа только с клавиатуры. Разные часовые пояса тоже стоит проверить, хотя бы потому что `cron` в Actions задаётся в UTC и это легко неправильно понять.

## Какие данные вводить

Тут я бы шёл от граничных значений и всего «странного», что может прийти от пользователя.

- **Имена репозиториев и веток:** пустое, один символ, максимальная длина и на один больше, точка, две точки, пробелы, кириллица, эмодзи. Ещё интересный случай: ветка и тег с одинаковым именем.
- **Текст issue и комментариев:** очень длинный (десятки тысяч символов), только пробелы, невидимые символы, текст справа налево, огромная таблица в Markdown.
- **Попытки XSS в Markdown:** `<script>`, `<img onerror=...>`, ссылки с `javascript:`. Скорее всего это давно закрыто, но проверить надо, особенно в менее очевидных местах вроде превью SVG и Jupyter-ноутбуков.
- **Ссылки и упоминания:** `#123` или `org/repo#1`, указывающие на приватный репозиторий. Не покажет ли GitHub человеку без доступа название issue или хотя бы сам факт, что он существует?
- **Файлы:** пустой, ровно на лимит, бинарник с расширением `.md`, файл с одной огромной строкой, PR с очень большим diff.
- **Коммиты:** пустое сообщение, дата из будущего или 1970 год, автор с левым email.
- **Параметры API:** номер issue 0, -1 или огромное число, `per_page=0` и больше максимума.

## Где я вижу риски

Расположил примерно в порядке того, насколько это было бы плохо.

1. **Обход прав.** То, что запрещено в интерфейсе, разрешено через API или git. Если такое найдётся, это критично.
2. **Доступ к чужим объектам по id.** Подставить в запрос номер чужого приватного issue или id чужого объекта и посмотреть, что вернётся.
3. **Секреты в Actions.** Насколько я знаю, это реальная больная тема: workflow, запущенный из форка, при неправильной настройке (например, через `pull_request_target`) может получить доступ к секретам основного репозитория. Сюда же логи и артефакты, в которых случайно светятся токены.
4. **Отзыв доступа работает не сразу.** Права закешированы, старый токен ещё живёт и т.п.
5. **Утечка информации о приватных репозиториях** через упоминания, уведомления или поиск.
6. **Гонки при merge.** Двойной merge, merge в момент, когда статус проверок поменялся.
7. **Вебхуки.** Повторная доставка, другой порядок событий. Это скорее риск для тех, кто их принимает, но со стороны GitHub тоже стоит понимать гарантии.
8. **Большие данные.** Огромные PR, монорепозитории, тысячи комментариев. Интерфейс может начать тормозить или обрезать данные.
9. **Рассинхрон.** Сразу после изменения UI и API показывают разное, например статус проверок или можно ли смержить PR.
10. **Rate limit.** Не очень опасно, но интересно, насколько понятная ошибка приходит и одинаково ли себя ведут разные клиенты.

Важный момент: всё, что связано с безопасностью, я бы проверял только на своих тестовых аккаунтах и репозиториях. А если бы реально что-то нашёл, то сообщал через bug bounty, а не открывал публичный issue.

## Как бы я оформлял найденный баг

Чтобы было понятно, что я имею в виду, вот пример. Это сценарий для проверки, а не подтверждённый баг:

> **Комментарий пропадает без предупреждения при обрыве сети**
>
> Chrome, Windows 11, github.com
>
> 1. Открыть любой issue и написать длинный комментарий.
> 2. В DevTools включить режим Offline.
> 3. Нажать «Comment».
> 4. Вернуть сеть и обновить страницу.
>
> Ожидаю: понятную ошибку и сохранённый черновик.
> Фактически: *(что получится при проверке)*
>
> Приложить видео и HAR-файл.

## Что бы я спросил у разработчиков

Многие вещи без команды не понять, потому что непонятно, баг это или так задумано. Вопросы, которые я бы задал:

- Какие функции самые важные для бизнеса? Где за последнее время было больше всего инцидентов?
- Если документации нет, где тогда смотреть, как должно работать? В тикетах, в макетах, где-то ещё?
- Права доступа проверяются в одном месте или отдельно в каждом клиенте и API?
- Как быстро должен применяться отзыв доступа? Есть ли кеш прав?
- Что происходит в фоне и с какими гарантиями: сколько может быть задержка, повторяются ли события, сохраняется ли порядок?
- Как защищён merge от двойного выполнения?
- Есть ли тестовый стенд, тестовые организации, можно ли включать фичи через feature flags?
- Как найти логи по конкретному запросу, если я поймал баг?
- Какие браузеры и версии мобильных ОС официально поддерживаются?
- Что уже покрыто автотестами, а где их почти нет?
- Как устроены релизы и можно ли быстро откатиться?

## Что бы я автоматизировал

Если бы после недели дали время на автотесты, я бы начал с таблицы прав доступа через API. Её долго проходить руками, она важная и её нужно перепроверять на каждом релизе. Потом основной сценарий «ветка → PR → проверки → merge» через `gh` и API, и проверки ответов API (формат, коды ошибок, пагинация). Набор странных входных данных из раздела выше тоже хорошо ложится в параметризованные тесты. А браузерные E2E-тесты оставил бы только для пары самых важных сценариев, потому что они медленные и часто ломаются от изменений вёрстки.

## Вывод

За неделю я бы, наверное, не нашёл много реальных багов. GitHub всё-таки большой и зрелый продукт. Но я бы понял, как он устроен, и знал, куда смотреть дальше. Для меня самые подозрительные места не в самом интерфейсе, а на стыках: между сайтом, API и git, между тем, что происходит сразу и что в фоне, и между разными ролями пользователей. Туда я бы и тратил основное время.
